# スカル

3〜6人用。ゲーム一覧から選択し、同じルームで遊びます。基本の遊び方は
`src/games/catalog.ts` にあります。

- 花3枚・ドクロ1枚から開始。最初の1枚は全員同時に伏せ、その後は座席順で追加か宣言。
- 宣言後は上乗せかパス。場の全枚数を宣言するか、他全員がパスするとチャレンジ。
- 自分の山を先に、各山の上から1枚ずつめくります。宣言数に達した時点で成功。
- 他人のドクロで失敗すると、場に置いた分を含む所有ディスクからランダムで1枚失います。
  自分のドクロなら本人が選びます。失った種類は本人以外に公開しません。
- 2回成功、または最後の生存者が勝利。0枚で脱落し、以後は観戦できます。
- 最初の先手はランダム。以後は挑戦者、挑戦者が脱落したらドクロの持ち主。
  自分のドクロで脱落した場合は本人が次の先手を選びます。
- ホストが結果画面から次ラウンドへ進めます。終了後はロビーへ戻ります。
  共通ヘッダーからのホストによる中断も利用できます。

## 秘密情報と再接続

`rules.ts` が進行と公開・本人用データへの変換を担います。秘密状態は
`private.skull_state` に保存し、ブラウザの直接参照を禁止します。
認証付き `/api/skull` は所属を確認し、取得者本人の情報だけを追加して返します。
共有のルームデータには伏せた種類・手札・失った種類を含めません。
失った後も場の履歴を保持し、公開済みの位置から喪失種類を逆算できないようにします。
本人の手札・伏せた山も通常は隠し、長押し中だけ表示します。

更新はルームのロックとリビジョン比較で確定し、プレイヤー別操作IDで再送を除外します。
初回配置は競合時に再試行し、順番制の操作は古い状態から実行できません。
ロビーへのリセットでは世代番号を増やし、古い初期化や通信結果を拒否します。

## 本番反映

1. `supabase/migrations/20261126000000_add_skull.sql` を適用する。
2. サーバーの `SUPABASE_SERVICE_ROLE_KEY`、通常のSupabase URL・匿名キーを確認する。
   サービスキーは公開用環境変数にしない。
3. アプリをデプロイする。
4. 実際の複数端末で3人・6人の開始、再接続、脱落、勝利、ロビー復帰を確認する。

## 検証

`npm test -- --maxWorkers=1`、`npm run typecheck`、`npm run lint`。
ゲームルール、APIの認証・競合・再送、PGlite上のDB権限・リセット、画面の秘密表示、
ルーム統合を自動テストします。実SupabaseのRealtimeとスマホ操作は別途実機確認が必要です。
